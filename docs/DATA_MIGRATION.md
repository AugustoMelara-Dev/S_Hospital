# Data Migration And Export Runbook

## Scope

S_Hospital is closed as software and runs as a local Laravel, React, and
MySQL/MariaDB system. This runbook documents operational data movement for the
current `main` implementation. It does not authorize production restore,
physical go-live, or schema changes.

## Supported Paths

- Full backup: generated by the real backup flow and stored as `.sql.enc`.
- Backup integrity: verify `backup_logs.checksum_sha256` or an operator-supplied
  SHA256 before restore.
- Reports and exports: use current Reports, Invoice History, CashBox, and
  Backups screens according to role permissions.
- Migration between machines: install the same release, restore into a
  disposable database first, then request operational approval before touching
  the active database.

## Rules

- Do not restore over production as a test.
- Do not export real patient data for development or support.
- Do not copy `.env`, APP_KEY, database passwords, or backup secrets into issue
  reports.
- Do not import legacy branch scripts unless they are reviewed against current
  `main`.

## Disposable Restore Checklist

1. Create a separate MySQL/MariaDB database, user, and volume.
2. Use only synthetic or approved backup data.
3. Verify the backup file is non-empty and has the expected SHA256.
4. Restore into the disposable target.
5. Compare critical counts: users, roles, services, invoices, invoice items,
   payments, cash sessions, cash movements, receipts, and fiscal sequences.
6. Start backend/frontend against the restored target and verify login plus
   critical reads.
7. Destroy the disposable target after evidence is recorded.

## Status

Software development is closed. External operational acceptance remains
deferred until an operator runs the physical/LAN gates.
